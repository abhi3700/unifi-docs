UniFi supports product teams that need stablecoin payments without pushing wallet and settlement
complexity into every customer journey. Use the web app for operator workflows and the API for
server-side integrations.

## Integration flow

<Steps>
  <Step title="Create API access">
    Sign in to UniFi, open **More → API**, and create a key for the service that will call the API.
  </Step>
  <Step title="Collect payment details">
    Define the stablecoin, network, recipient, amount, fee mode, and any reference your product
    needs to reconcile the transfer.
  </Step>
  <Step title="Authorize the payment">
    Keep approval in the account's security boundary. Email accounts use authenticator approval;
    connected wallets approve and sign through the wallet when required.
  </Step>
  <Step title="Store the receipt ID">
    Save the returned receipt identifier with your own order or invoice record. It is the stable
    reference for status checks and support.
  </Step>
  <Step title="Wait for finality">
    Treat `Submitted` and `Confirmed` as in progress. Complete the business action only after the
    receipt reaches `Finalized`.
  </Step>
</Steps>

## Recommended boundary

```text
Your client → Your trusted backend → UniFi API → Network settlement → Receipt
```

Keep API keys in a trusted backend. Do not embed them in browser code, mobile binaries, public
configuration, analytics events, or shared logs. Wallet signatures belong in the user's wallet;
UniFi never needs a seed phrase or private key.

## Design for asynchronous settlement

Submission and finality are separate events. Your integration should persist the receipt ID,
display an in-progress state, tolerate repeated status checks, and make the final business action
idempotent. A retry must not create a second order or release the same goods twice.

<Note>
Use the API base URL and credentials issued for your UniFi deployment. Credentials are scoped to
their assigned environment and should not be mixed across deployments.
</Note>

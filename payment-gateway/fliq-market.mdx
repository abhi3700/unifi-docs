## Complete payment journey

The landing page uses FliQ Market to show the full reference flow—from browsing a product through
receipt finality and order fulfillment. The merchant keeps ownership of the checkout and order,
while the widget supplies the reusable UniFi payment, status, and receipt experience.

## Payment states

- `Processing` — **Payment submitted**; the order is not confirmed;
- `Confirmed` — included on-chain and waiting for finality;
- `Finalized` — payment complete and the order can enter fulfillment; and
- `Failed` or `Reorged` — unsuccessful terminal state, so the order remains unconfirmed.

While finality is pending, the page checks again every 15 minutes to conserve API credits. A refresh
icon lets the customer request an immediate check without waiting for the next automatic interval.
Terminal states remove that action because no further status check is needed.

## Configuration boundary

FliQ Market uses one Cloudflare Pages Function for two responsibilities:

- `GET /api/config` returns the public `MERCHANT_WALLET_ADDRESS` and optional local checkout
  override; and
- `/api/unifi/payment/merchant/session/:sessionId` delegates to the widget's narrow server proxy,
  which reads `UNIFI_API_KEY` only in the server runtime.

```makefile
UNIFI_API_KEY=
MERCHANT_WALLET_ADDRESS=
```

The API base URL and web-app base URL are optional UniFi admin/local overrides. Leave them unset in
a normal merchant production deployment.

## What to copy—and what to replace

Copy the integration boundaries: public recipient configuration, server-only API key, shared widget
components, session persistence, same-origin status checks, and receipt reconciliation.

Replace the demo commerce layer with your own trusted catalog, pricing, tax, inventory, order,
fulfilment, and customer-support systems. FliQ Market demonstrates the payment integration; it is
not a production order database.

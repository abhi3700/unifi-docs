UniFi's goal is to make stablecoin payments feel like a familiar payment app while preserving the
onchain record behind every transfer. The experience centers on three things: a wallet view, a
send/receive flow, and a receipt that follows a payment through finality.

## One rail, multiple interfaces

UniFi's web app is the direct user experience. The API and developer kit expose the same payment lifecycle to applications. The payment gateway packages collection flows for merchants, while Falcon coordinates payment automation.

<Info>
    “Gasless” describes the supported payment execution flow. A first-time token
    approval is an onchain transaction and can still require the network's
    native gas token.
</Info>

## What the current product supports

The web app and backend currently implement:

- email accounts with a UniFi-managed wallet and authenticator-based approval for protected actions;
- self-custodial EVM wallets connected through MetaMask;
- USDT, USDC, and DAI payment choices;
- Ethereum, Polygon, and Sepolia network choices;
- fee-inclusive and fee-exclusive payments;
- payment links and QR requests through FliQR;
- searchable payment history and receipts with `Submitted`, `Confirmed`, and `Finalized` stages;
- API keys, usage quotas, and API-plan selection.

<Note>
    The exact assets and networks available to a user can vary by account and
    product configuration. Use the choices displayed in the app when starting a
    payment or deposit.
</Note>

## Product principles

### Make the payment explicit

A payment always names the stablecoin, network, recipient, amount, and fee mode. The review step
keeps those choices visible before the user authorizes anything.

### Separate authorization from execution

Email accounts approve sensitive actions with authenticator OTP. A self-custodial wallet approves
Permit2 when required and signs payment-specific data. UniFi's execution layer then validates and
submits the transfer.

### Treat finality as part of the product

Submission is not the same as settlement. Receipts distinguish a request accepted by UniFi from a
transaction confirmed onchain and a block considered finalized.

### Keep developer access visible

The same web app exposes API-key management, credit usage, request-rate limits, and plan choices so
an integration can be operated alongside end-user payments.

## Product direction, not current behavior

The UniFi roadmap includes broader payroll, scheduled-payment, cross-chain, and token-routing
goals. Those are product direction. This documentation presents a feature as available only when
it is offered by the application or public API.

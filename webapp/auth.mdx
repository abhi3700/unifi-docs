Auth is the gate for wallet, payment, history, and API-management routes. The route stores the page
the user originally requested and returns there after a successful session is established.

Email and Unio are available on web, PWA, and native apps. Web and PWA layouts above 699px also
offer MetaMask for sign-in and wallet switching.

## Email account flow

For a new email account, the implementation proceeds through:

<Steps>
    <Step title="Verify the email">
        Enter a valid email address and submit the six-digit OTP sent by the
        configured email service.
    </Step>
    <Step title="Set a password">
        The password is hashed client-side with the account identifier before
        the login request.
    </Step>
    <Step title="Enable authenticator 2FA">
        Scan the generated TOTP QR and confirm a current six-digit code.
    </Step>
    <Step title="Open the requested page">
        The web session is stored in the `unifi_user_id` and `unifi_jwt` cookies
        and the original route is resumed.
    </Step>
</Steps>

Returning email users complete password and authenticator checks when the backend reports that a
fresh login is required. Recovery routes exist for password reset and 2FA renewal.

## Unio flow

Choose **Unio** to [create or import a wallet](/webapp/unio#set-up-the-wallet). When you return,
unlock it with your wallet password or biometrics if enabled. When UniFi needs a new session,
Unio signs the authentication challenge on your device.

## MetaMask flow

The app requests a server-issued challenge, asks MetaMask to sign it, and exchanges the signature
for a web JWT. The server checks that the challenge address, origin, chain context,
nonce, and expiry match before issuing the session.

The challenge endpoints do not require an existing bearer credential.

<Steps>
    <Step title="Request a challenge">
        POST the expected domain, URI, and chain ID for the wallet address. The
        server returns a short-lived message, nonce, and expiry.
    </Step>
    <Step title="Sign the exact message">
        Ask the wallet to sign the returned message without altering whitespace
        or fields.
    </Step>
    <Step title="Exchange it for a JWT">
        POST the message, signature, nonce, and platform. The challenge is
        single-use.
    </Step>
    <Step title="Send the JWT">
        Use the returned JWT as the bearer credential for protected user routes.
    </Step>
</Steps>

<Warning>
    Validate that the challenge domain and URI match the application the user is
    viewing. Reject expired challenges and never reuse a nonce.
</Warning>

<Note>
    Email-based and AWS KMS integrations authenticate through their managed
    UniFi flow. The signed challenge described here is specifically for
    self-custodial wallets.
</Note>

<Warning>
    Sign in by signing the wallet challenge. If you import a wallet into Unio, enter its recovery
    phrase or private key only in Unio's local import screen. UniFi servers never receive either.
</Warning>

## Session exit

Email accounts log out; connected-wallet accounts disconnect. Protected pages reuse the shared
logout/disconnect dialog and return to Auth when the session is missing or invalid.

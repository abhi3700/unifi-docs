Auth is the gate for wallet, payment, history, and API-management routes. The route stores the page
the user originally requested and returns there after a successful session is established.

## Email account flow

For a new email account, the implementation proceeds through:

<Steps>
  <Step title="Verify the email">
    Enter a valid email address and submit the six-digit OTP sent by the configured email service.
  </Step>
  <Step title="Set a password">
    The password is hashed client-side with the account identifier before the login request.
  </Step>
  <Step title="Enable authenticator 2FA">
    Scan the generated TOTP QR and confirm a current six-digit code.
  </Step>
  <Step title="Open the requested page">
    The web session is stored in the `unifi_user_id` and `unifi_jwt` cookies and the original route
    is resumed.
  </Step>
</Steps>

Returning email users complete password and authenticator checks when the backend reports that a
fresh login is required. Recovery routes exist for password reset and 2FA renewal.

## MetaMask flow

The wallet flow requests a server-issued challenge, signs it in MetaMask, and exchanges the
signature for a web JWT. The server checks that the challenge address, origin, chain context,
nonce, and expiry match before issuing the session.

<Warning>
UniFi never needs a seed phrase or private key. A legitimate login asks the wallet to sign the
displayed authentication challenge, not to reveal wallet secrets.
</Warning>

## Session exit

Email accounts log out; connected-wallet accounts disconnect. Protected pages reuse the shared
logout/disconnect dialog and return to Auth when the session is missing or invalid.
